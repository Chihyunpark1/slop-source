# Background workers audit — entry points, schedules, bindings, and fund flows verified from code (Issue #13)

## Target

The 13 background workers of the public SLOPCASH codebase
(`SlopDotCash/slopdotcash`, MIT) at development commit
`ced75d782d5836f60d84f46d50604f75a5852438`: the directories
`workers/fee-converter`, `workers/identity`, `workers/notify`,
`workers/operator-keeper`, `workers/payment-executor`,
`workers/payments`, `workers/referral-accrual`,
`workers/security-payments`, `workers/slopbot`, `workers/vetting`,
`workers/vetting-backup`, `workers/vetting-flags`, and
`workers/vetting-sandbox` — their entry modules, exported handlers,
checked-in Wrangler configuration (name, cron triggers, bindings),
and the code paths that generate configuration where no checked-in
`wrangler.toml` exists.

The packet is this file; the checker is `scripts/audit-workers.py`;
its tests are `tests/test_audit_workers.py`. This is a code audit,
not a summary: open PR #29 already inventories the 13 components in
prose for issue #18 at an older commit; this packet instead parses
the configuration and entry modules mechanically at the current
commit and reports what the parser finds, including the five
components that have no checked-in `wrangler.toml` at all.

## Claim

The "13 background workers" are exactly the 13 directories under
`workers/` at the pinned commit — no more, no fewer — but they are
not 13 alike deployments: only 8 carry a checked-in production
`wrangler.toml`; 2 (payments, payment-executor) get their
configuration generated by release code; 1 (security-payments) is a
scheduled-only wrapper that reuses the payments entry with a swapped
ledger; 1 (vetting) is a service library executed by a GitHub
Actions cron, not a deployed Worker; and 1 (vetting-flags) is a
qualification fixture set that is never deployed. Four of the 13
move funds (fee-converter, payments, payment-executor,
security-payments), one is an operator-owned payment-keeper template
(operator-keeper), one files reward accruals while its program flag
is off (referral-accrual), and seven never touch funds.

Per-worker notes, each pinned to the code:

- **The count is mechanical, and it holds.** `workers/` contains
  exactly the 13 directories named in issue #13, plus three shared
  modules that are not workers (`verified-budget.ts`,
  `verified-fee-replacement.ts`, `verified-policy.ts`).
- **Handler census.** 10 of 13 export a `scheduled` handler, 9
  export `fetch`, and only 2 export a `queue` handler (slopbot,
  vetting-backup). Two of the `fetch` exports are stubs that always
  answer 404 (fee-converter `index.ts`, referral-accrual
  `index.ts`), so a `fetch` export does not by itself mean a public
  route.
- **fee-converter schedule detail.** The single per-minute cron
  does double duty: at minutes divisible by 15 the scheduled handler
  runs a full recovery scan instead of the receipts pass
  (`triggerAt` in `workers/fee-converter/index.ts`, keyed on
  `RECOVERY_SCAN_MINUTES`).
- **notify's empty cron list is the default profile, not a
  missing schedule.** Its `wrangler.toml` states that the checked-in
  release has no pilot schedule and that `scripts/release-notify.mjs`
  adds the selected environment's D1 binding and schedule only for
  an explicit pilot (comment above `[triggers]`,
  `workers/notify/wrangler.toml:25-26`).
- **operator-keeper is not Slop infrastructure.** Its configuration
  header calls it an independent operator template that is never
  included in Slop's deployment workflow, its mode variable defaults
  to `off`, and its README states the operator supplies their own
  account, gas wallet, and spending limits
  (`workers/operator-keeper/wrangler.toml:1-13`,
  `workers/operator-keeper/README.md`).
- **payment-executor's cron lives in a generator.**
  `workers/payment-executor/configure.mjs:332` emits
  `triggers: { crons: [] }` for the keeper topology and
  `["*/5 * * * *"]` otherwise; no `wrangler.toml` is checked in.
- **payments has no fetch handler and no checked-in cron.** Its
  default export is `scheduled` only
  (`workers/payments/index.ts:684-711`), and its deployment
  configuration is produced during release
  (`scripts/prepare-payment-deployments.ts`, invoked from
  `.github/workflows/deploy.yml`).
- **security-payments is 32 lines.** It builds a private environment
  (`PAYMENT_SCOPE: "security-bounty"`, `PAYMENTS_DB` swapped to the
  security ledger derived from `REGISTRY_DB`), runs one outbox
  update, and delegates to the payments scheduled handler
  (`workers/security-payments/index.ts:6-32`).
- **slopbot's real entry is a re-export.** The configured `main` is
  `entrypoint.ts`, which re-exports the default export of
  `index.ts` and adds two `WorkerEntrypoint` classes,
  `ReportingReadinessRefresher` (consumed by identity) and
  `HistoricalValuePublisher` (`workers/slopbot/entrypoint.ts:1-3`;
  handlers at `workers/slopbot/index.ts:237,522,542`).
- **vetting runs on Actions time.** The controller workflow runs
  every 15 minutes (`7,22,37,52 * * * *`,
  `.github/workflows/vetting-controller.yml:3-4`) and invokes
  `bun scripts/run-vetting-controller.ts` (line 98), which drives
  the service pass documented at the top of
  `workers/vetting/run.ts`. There is no `wrangler.toml` and no
  Worker default export in `workers/vetting/`.
- **vetting-backup's entry is `core.ts`, not `index.ts`** — the
  only worker whose configured `main` is not an index/entrypoint
  file (`workers/vetting-backup/wrangler.toml:2`).
- **Activation states are configuration, not observation.**
  Checked-in variables show fee-converter mode `live` for the
  base/ethereum/robinhood networks with Solana deferred
  (`workers/fee-converter/wrangler.toml` vars and comments),
  referral-accrual mode `off` with its program flag `"false"`,
  vetting-backup modes `off`, and slopbot closures disabled
  (`SLOPBOT_CLOSURE_ENABLED = "false"`). These are the values the
  public tree declares; which of them the live deployment currently
  runs cannot be read from the tree.

## Verification

- Ran the checker against a fresh checkout of the target commit:
  `python3 scripts/audit-workers.py <checkout>` printed
  `workers/ directories: 13`, the table and bindings reproduced
  above, the census lines `8 with a checked-in wrangler.toml; 5
  without`, `9 of 13 export a fetch handler`, `10 of 13 export a
  scheduled handler`, `2 of 13 export a queue handler`, and
  `result: ALL CHECKS PASSED` (the directory set equals the 13
  names in issue #13 exactly).
- Ran the script's tests: `tests/test_audit_workers.py` builds a
  synthetic `workers/` tree and checks the count, the TOML parsing,
  the re-export hop, the empty-list versus missing-triggers
  distinction, and the failure case — 4 passed; the pre-existing
  `tests/test_verify_selector.py` still passes (4 passed).
- Spot-checked the parser's output by hand against the files it
  parsed: every cron string in the table matches the `[triggers]`
  section of the corresponding `wrangler.toml` (fee-converter:14,
  identity:38, notify:28, operator-keeper:12, referral-accrual:14,
  slopbot:35, vetting-backup:12), and the two generated/generated-by
  cases match `configure.mjs:332` and the release workflow.

## Notes

- **Public versus live.** Everything above is public code and
  checked-in configuration. Not observable from public material:
  which generated payment configurations are currently deployed,
  which pilot schedules the notify release script has added, live
  queue depths, and whether live variable values differ from the
  checked-in ones. This packet claims none of those.
- **Boundaries.** Payout-path internals for payments,
  payment-executor, and security-payments are covered by PR #32 and
  are cited here only at the boundary. Slopbot's points, penalty,
  and appeal internals are covered by PR #23. The prose inventory
  for issue #18 is PR #29; this packet is the parsed audit for
  issue #13 and re-pins everything to the current development
  commit.
- **One judgment call, stated openly.** referral-accrual sits in
  its own class because its checked-in mode is `off` and its
  program flag is `"false"`: the code can post distribution roots
  in live mode, but as checked in it files accrual records only.
